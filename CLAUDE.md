# Red Human AI — Reglas del proyecto

Plataforma SaaS de agente de IA de RH para México. `red-human-app` (Next.js 15) + `red-human-api` (FastAPI). Respuestas y UI en español mexicano.

## Claves y seguridad

- Las claves viven SOLO en `red-human-api/.env` (gitignored). Nunca en código, ni en el bundle del cliente, ni pegadas en chats.
- `OPENAI_API_KEY` → cerebro de toda la IA (modelo en `OPENAI_MODEL`, hoy `gpt-5.6-luna`).
- `ANAM_API_KEY` → avatar de entrevistas. NUNCA exponerla al navegador: los session tokens se generan en el servidor (`app/services/avatar.py`) y solo el token efímero (~1 h) llega al cliente.
- El endpoint de OpenAI está registrado en Anam como LLM propio (`ANAM_LLM_ID`); para rotar la clave de OpenAI hay que actualizar también esa registración (`POST https://api.anam.ai/v1/llms`).
- Todo `personaConfig` inline debe incluir `llmId`, o Anam rechaza el token como "legacy".

## Avatar de entrevistas (Anam)

- Anam escucha (STT), habla (TTS) y pone la cara; el que piensa es NUESTRO modelo de OpenAI.
- El endpoint del LLM debe soportar streaming.
- Respuestas del agente breves y conversacionales: se dicen en voz alta.
- Preparar en page-load (SDK precargado, `preconnect` a api.anam.ai); el clic del usuario solo inicia el stream.
- Usar avatares neutrales del catálogo de Anam — nunca clones de personas reales sin consentimiento expreso (reforma de derecho de autor 2026).

## WhatsApp (Meta Cloud API)

- `WHATSAPP_PROVIDER=meta`. El token (`META_WHATSAPP_TOKEN`) vive solo en el servidor; nunca al navegador.
- El webhook `POST /webhooks/whatsapp` es público: valida siempre la firma `X-Hub-Signature-256` con `META_APP_SECRET`. (2026-10-08, `webhooks.verificar_firma_whatsapp`, sobre el cuerpo CRUDO y ANTES de leerlo: con secreto, sin firma válida → 403; `WHATSAPP_PROVIDER=meta` sin secreto → 503; otros proveedores sin secreto aceptan mensajes pero los acuses de entrega NUNCA se procesan sin firma verificada). Las verificaciones que simulan Meta firman el cuerpo.
- El webhook contesta 200 de inmediato y corre el prefiltro en segundo plano — Meta reintenta si tardas, y se deduplica por `wamid`.
- Teléfonos: en la base se guardan a 10 dígitos; hacia la API salen como `52` + 10 (sin el `1`, que Meta ya no usa).
- Ventana de 24 h: fuera de ella Meta rechaza el texto libre (error 131047) y hay que usar plantilla aprobada (`META_PLANTILLA_AVISO`).
- Ningún mensaje saliente decide nada: sigue siendo la persona de RH quien avanza o descarta.

## Legal (México)

- LFPDPPP 2025: la IA solo recomienda; avanzar/descartar/alta siempre lo decide una persona de RH con nombre registrado en bitácora (human-in-the-loop).
- Consentimiento explícito del candidato antes de cualquier entrevista o tratamiento de datos; queda en la bitácora hash-encadenada.
- No pedir ni inferir datos sensibles (salud, embarazo, religión, estado civil, orientación).

## Fase 2 — Candidato (persona) vs Postulación (proceso)

- `Candidato` = identidad (nombre, teléfono, correo, wa_id, CV, archivos). `Postulacion` = una aplicación a una vacante: etapa, estado, score, chat, entrevistas, expediente. **Ningún endpoint escribe estado de proceso en `Candidato`** (sus columnas de proceso son legado solo para `scripts/migrar_postulaciones.py`).
- Kanban: una tarjeta por Postulación; `id`/`candidatoId` en la API es el código `P-####` (lo que se manda a `/candidatos/{codigo}/...`); la persona va en `candidatoCodigo`. Se acepta `C-####` por compatibilidad.
- Expediente pertenece a la Postulación (una persona puede tener varios a lo largo del tiempo).
- Reaplicar: si hay postulación ACTIVA para esa vacante se reutiliza; si está cerrada (`descartado`/`contratado`/`reinicio_prueba`) se crea una nueva y la vieja queda como historial. `descartar` cierra; mover de etapa reabre.
- WhatsApp: elegir vacante del menú NUNCA es consentimiento — siempre aviso de privacidad + "Sí"/"Acepto" explícito (palabra completa, `_es_aceptacion`) antes de iniciar el prefiltro; solo se omite si la postulación ya tenía consentimiento registrado por otro medio (RH / `/aplicar`).
- WhatsApp: `Candidato.postulacion_conversacion_id` es la postulación en chat. Lo mueve SOLO el candidato (mensaje entrante enrutado o selección explícita en lista); un mensaje saliente de RH/sistema NUNCA lo mueve (B1). Si el puntero no sirve y varias postulaciones esperan respuesta (`Postulacion.espera_respuesta`), el webhook manda lista interactiva (ids `P-####`) y NO adivina. Ver docstring de `routers/webhooks.py`.
- Crear postulaciones SOLO con `candidatos.crear_postulacion` / `postulacion_para_vacante` (código `P-{8800+id}` de la propia postulación).
- Kanban (B4): `GET /candidatos` regresa solo postulaciones activas salvo `mostrar_cerradas=true` (toggle "Mostrar cerradas") o `activa=` explícito.
- Base existente: correr `scripts/migrar_postulaciones.py --forzar` una vez ANTES de arrancar la versión nueva; la API se niega a arrancar (RuntimeError en lifespan) si hay candidatos sin postulación — la migración de datos nunca corre sola. Prueba de regresión: `scripts/verificar_fase2.py` (modo demo, base desechable).

## Configuración administrativa (Puntos 9-13)

- Cuentas: un Administrador solo ve/administra las Cuentas vinculadas a él (`usuario_cuentas`); `GET/PATCH /cuentas/{id}` responde 404 para una ajena. `Cuenta.nombre` (interno) ≠ `nombre_comercial` (candidatos); leer siempre `nombre_visible`.
- Notificaciones: `services/notificaciones.disparar(..., override=)` acepta ajustes SOLO para esa acción (`NotificarIn`, body `notificar`); la regla guardada nunca se toca desde una acción. Los eventos automáticos (`candidato_apto`, no-show, liga externa) nunca mandan override. En el frontend, toda acción manual que notifica pasa por `LineaNotificar`/`ConfirmacionAccion`.
- Plantillas: el contenido compartido Vacante↔Plantilla es `models.CAMPOS_PLANTILLA` (única lista); el formulario de contenido es uno solo (`components/dashboard/vacantes/formulario-contenido.tsx`) para Nueva vacante y Configuración → Plantillas.
- Modo Prueba: la ventana de nueva sesión se lee de `ConfiguracionSistema.modo_prueba_ventana_min` (nunca hardcodearla).
- Al cambiar de Cuenta, `<PorCuenta>` (layout del dashboard) remonta todo el árbol: no cachear datos por Cuenta fuera de React.

## Entrevista IA (Fase 4)

- Toda identidad de empresa en contenido generado por IA (vacantes, WhatsApp, entrevista) sale de UNA regla: `serial.nombre_empresa(cuenta, cliente, mostrar)` / `nombre_empresa_candidato(v)` → Cliente visible si "mostrar cliente al candidato", si no el nombre comercial de la Cuenta. Nunca texto libre.
- Nombre del candidato: siempre el de la ficha (`candidatos.nombre_ficha(p)`); el perfil de WhatsApp (`wa_nombre`) solo si la ficha trae placeholder. Contexto de la entrevista siempre desde `e.postulacion` (nunca desde la persona).
- La entrevistadora se presenta SOLO como «Red Human» (nunca con nombre de persona — "Alma" se eliminó —, nunca "asistente virtual" ni "agente de inteligencia artificial"; si le preguntan si es IA lo dice con naturalidad). Introducción EXACTA en `ia.mensaje_inicial_entrevista(titulo_vacante)` con el nombre real de la vacante; tras la respuesta del candidato inicia de inmediato sin transición; silencio `ia.AVISO_SILENCIO`; sin numerar preguntas; una pregunta principal por turno; despedida fija `ia.DESPEDIDA_ENTREVISTA`. El aviso "conversas con una IA" vive solo en la pantalla de consentimiento (LFPDPPP).
- Cierre verificable: el backend solo cierra una entrevista con `POST /finalizar` y verifica el `cierre` declarado contra el transcript (`_cierre_verificado`); sin señal verificable degrada a `manual`; desconexión con <2 turnos → `interrumpida` (RH reabre con `POST /entrevistas/{codigo}/reabrir`). Nunca cerrar por tiempo en el servidor sin señal.
- Enfoque de entrevista por vacante: SOLO 2 niveles (`profesional` | `profesional_personal`, `models.ENFOQUES_ENTREVISTA`). No agregar más.
- Datos sensibles (`ia.DATOS_SENSIBLES_PROHIBIDOS`): ni preguntar ni registrar aunque el candidato los mencione — aplica al entrevistador y al evaluador.

## Formulario de vacante (Parte 3)

- Orden fijo del formulario compartido (`components/dashboard/vacantes/formulario-contenido.tsx`, Nueva vacante Y Plantillas): Datos principales → Guía opcional → [Generar vacante con Red Human] → Contenido generado y editable → Selección (Prefiltro → Entrevista Red Human) → Gestión → Publicación. El botón de generar va ABAJO de la captura, nunca arriba. No existe "Notas para la IA".
- Regla no negociable 1: Red Human NUNCA inventa condiciones reales (sueldo, periodicidad, ubicación, modalidad, horario, prestaciones). Lo que RH no capturó queda vacío/pendiente con aviso; `beneficios` = exactamente los capturados; `rango_salarial_sugerido` es solo informativo. Garantizado en `ia._asegurar_capturado` (IA y demo) — no depende del prompt.
- Regla no negociable 2: lo capturado se respeta literal — indispensable sigue indispensable, deseable sigue deseable, seniority el elegido; la IA solo AGREGA/complementa lo vacío (`_unir_capturado`, `contenidoDesdeGenerado`). La descripción breve es guía y se expande.
- Sueldo: se captura ESTRUCTURADO (`sueldo_desde/hasta/moneda/periodicidad`, `PERIODICIDADES_SUELDO`); `Vacante.sueldo` (texto) es DERIVADO por `models.texto_sueldo` y es lo que leen WhatsApp, prefiltro, entrevista, portal, publicaciones y el agente. Nunca capturar ni editar el texto por separado. Seniority = uno de `ia.SENIORITY`.
- `Vacante.requisitos` sigue siendo texto (indispensables unidos por « · »); usa `routers.vacantes.requisitos_lista` / `requisitosLista` para tratarlo como lista.
- "Entrevista IA" es el valor interno de la etapa (base y API); en la interfaz la COLUMNA se muestra con `nombreEtapa()` → «Filtro Red Human» (2026-10-01; la actividad sigue llamándose «Entrevista Red Human»). No renombrar el valor almacenado.

## Entrevista Humana (Fase 7A)

- Entrevistador interno = `Usuario` de la Cuenta: nombre, correo y WhatsApp salen SIEMPRE del perfil (`Usuario.telefono`, capturado en Configuración → Usuarios); nunca se recapturan en la entrevista. `/auth/entrevistadores` los expone a cualquier sesión de la Cuenta.
- Entrevistador externo = `ClienteContacto` del Cliente de la vacante (`EntrevistaHumanaIn.entrevistador_contacto_id`, se guarda `EntrevistaHumana.contacto_id` y se copian nombre/correo/WhatsApp) o «+ Otro entrevistador» (captura manual). Nunca limitar a contactos registrados.
- Notificar al Cliente: `NotificarIn.cliente_contactos_ids` elige contactos ya registrados (None = todos, [] = ninguno); nunca se capturan datos nuevos del Cliente en una acción.
- Correo: `services/correo.py` (Resend). Sin `RESEND_API_KEY` no sale y se registra «RESEND_API_KEY sin configurar». 2026-09-18: el remitente es ESTRICTAMENTE `@redhuman.mx` (`correo.remitente()`: default `notificaciones@redhuman.mx`; un `RESEND_FROM` de otro dominio se ignora con warning) — el dominio debe estar verificado en Resend. Todo envío regresa `{destinatario, canal, destino, enviado, detalle}` y las acciones manuales lo muestran a RH (`lineasResultados`): un envío fallido nunca es silencioso.
- Las reglas de notificación de una Cuenta NACEN con `models.REGLAS_NOTIFICACION_DEFAULT` (entrevista_agendada = correo+WhatsApp a candidato y entrevistador); las reglas ya guardadas nunca se tocan automáticamente.

## Microsoft Teams (Fase 7B)

- Variables EXACTAS: `TEAMS_CLIENT_ID`, `TEAMS_TENANT_ID`, `TEAMS_CLIENT_SECRET` (+ opcional `TEAMS_REDIRECT_URI`). Solo en el `.env` del servidor; sin ellas `teams.teams_configurado()` es False y todo cae a la liga manual (mismo patrón que Resend/Anam: nunca rompe el flujo).
- OAuth con permisos DELEGADOS, conexión POR CUENTA (`IntegracionTeams`, una fila por Cuenta). Tokens SIEMPRE cifrados (Fernet con clave derivada de `TEAMS_CLIENT_SECRET`, `services/teams.py`); nunca se exponen por la API. Rotar el secret obliga a reconectar.
- La reunión se crea con `POST /me/events` (`isOnlineMeeting` + `teamsForBusiness`, asistentes = correos de candidato y entrevistador): Graph manda las invitaciones de calendario. Se crea ANTES de guardar la entrevista; si falla → 502 y no se guarda nada (decisión del usuario). Modificar/cancelar sincronizan la reunión best-effort (nunca bloquean).
- Con Teams conectado la UI NO pide la liga en Videollamada; «Usar otra liga» (`usar_teams=false`) es la excepción. No agregar modalidades ni pasos.

## Evaluación del candidato (2026-09-13)

- Prefiltro por WhatsApp = SOLO filtro de entrada: resultado `cumple` | `no_cumple`, sin score. `Postulacion.score` lo escribe únicamente el Análisis de CV. El prefiltro NO participa en la evaluación integral ni en la afinidad.
- Evaluación integral (`ia.evaluar_entrevista`) = Análisis de CV + Entrevista Red Human, nada más. Estructura: Afinidad (`match_perfil`), Fortalezas, Puntos por validar (`riesgos`), Recomendación, `faltante`.
- `/finalizar` valida el transcript antes de evaluar: sin respuestas útiles → `interrumpida` (`motivo=sin_respuestas`); pocas respuestas → `ia.suficiencia_entrevista` decide `parcial` (sin score) o evaluar indicando lo que faltó. Nunca generar score ni recomendar entrevista humana sin entrevista válida; la acción siguiente es «Reintentar Entrevista Red Human» (reabrir).
- La sala pública nunca debe quedar en negro: errores de sesión → fase `cerrada`/`error` con mensaje; fallo del avatar → sesión de texto forzada (`POST /sesion {"modo":"texto"}`); `error.tsx` en la ruta.
- Embudos y contadores por etapa cuentan solo postulaciones activas.

## Reglas de UI (reestructura 2026-09-16)

- Una sola acción principal visible por contexto; las secundarias van en `components/dashboard/menu-acciones.tsx` (`MenuAcciones`, menú «…»). Carga masiva = solo ícono con tooltip. Lo opcional vive en acordeones CERRADOS; sin "efecto libro". La IA automatiza primero; RH edita solo si quiere.
- Formulario de vacante: Datos principales (condiciones reales) → «Sobre la vacante» (descripción breve, indispensables, deseables, prestaciones, enfoque) → botón «Generar vacante con Red Human» → acordeón «Configuración avanzada» cerrado (responsabilidades, resumen, perfil ideal, palabras clave, prefiltro web, prefiltro WhatsApp, textos).
- Modo Prueba flexible: `services/configuracion.permite_duplicados(db)` — con Modo Prueba activo, teléfono/correo se repiten entre candidatos sin fusionar ni bloquear (cada alta es persona nueva); apagado → dedupe normal (nunca 409). El correo de login de `Usuario` es único SIEMPRE.
- Prefiltro dual (F2): la IA genera `preguntas_filtro` (web) y `preguntas_filtro_whatsapp` (2-3 puntos críticos, `ia.puntos_criticos_whatsapp` como fallback). `/postular` guarda `analisis.respuestas_web`; `candidatos.comparar_web_vs_whatsapp` detecta contradicciones → el agente manda UNA pregunta de aclaración (`aclaracion_pendiente`) y el siguiente turno la registra en `analisis.inconsistencias`. Con contradicción registrada la IA nunca descarta: un cierre `no_cumple` se convierte en `revision` para RH.
- Control manual (F2): `PATCH /candidatos/{codigo}/etapa {manual:true}` mueve a cualquier etapa (incluida Entrevista Humana sin agendar y Onboarding directo) y registra lo saltado en `Postulacion.actividades_omitidas` (usuario, fecha, motivo). Fallas de WhatsApp/correo nunca bloquean el movimiento. En la ficha: UNA acción principal + `…` con «Mover a otra etapa». Detalle de vacante = resumen + secciones plegadas (`Plegable`).
- Capacitación universal (F3): UN solo módulo y tipo de curso (`Curso` con `evaluacion` JSON integrada, `calificacion_minima`, `adjuntos`, `contexto`). Crear = tema + contexto opcional + adjuntos + duración → `ia.guion_curso` genera objetivo, categoría, módulos y evaluación (opción múltiple / V-F; `_asegurar_evaluacion` la garantiza). `AsignacionCurso.tipo` ∈ colaborador | candidato (`postulacion_id`) | externo (`externo_*`, liga abierta pide nombre + correo/WA en `/publica/{token}/registro`). Sala pública: `/avanzar` módulo por módulo, `/responder` una pregunta a la vez (nunca expone `correcta`), resultado Aprobado/No aprobado + % → `analisis.capacitacion` del candidato. `Vacante.curso_filtro_id` se asigna solo al quedar apto (`candidatos._asignar_curso_filtro`). Tablero único `GET /capacitacion/asignaciones` con filtros. Nada de plataformas externas ni módulos separados de evaluación.
- WhatsApp y vacantes (2026-09-16): el agente lee las vacantes de la base en CADA turno (`webhooks._vacantes_publicadas`, solo `Publicada`; no existe caché). Un proceso = pasos ubicados en esas etapas (`models.TIPOS_PASO`: prefiltro WhatsApp/web, Análisis de CV, Entrevista Red Human, los 7 tipos de evaluación, documentos, condiciones, tareas de Onboarding, alta), con dependencias EXPLÍCITAS (`depende_de`; sin dependencias = paralelo; nunca hacia una etapa posterior ni en ciclo), responsable (`RESPONSABLES_PASO`), condición de avance (`REGLAS_APROBACION`: ninguna | calificación mínima | dictamen aceptado | validación de RH) y plazo en días. Motor ÚNICO: `services/proceso.py`; API: `routers/procesos.py`; editor ÚNICO: `components/dashboard/procesos/editor-proceso.tsx`.
- Versionado SIEMPRE por copia: `PlantillaProceso` (Configuración → Procesos de selección; editar sube `version`; eliminar = desactivar; una `predeterminada` se copia sola a vacantes nuevas) → `Vacante.proceso` (sección «Proceso de selección» del formulario de vacante; personalizar no toca la plantilla; cada cambio sube su `version`) → `Postulacion.proceso` (CONGELADO al crear la postulación con `candidatos.crear_postulacion` / al elegir vacante por WhatsApp; `proceso.congelar` nunca reemplaza uno existente). Cambios en plantilla o vacante NUNCA tocan candidatos existentes; «Aplicar versión vigente» (`POST /procesos/postulaciones/{codigo}/aplicar-vigente`) es explícito y conserva como `heredado` (no obligatorio) todo paso con actividad que ya no exista. Vacante sin proceso: REEMPLAZADO por «Rutas de proceso» (abajo) — ninguna postulación queda sin ruta.
- Estado del paso ≠ resultado: estado `ESTADOS_PASO` (Pendiente / En curso / Completada / Omitida / Cancelada) y resultado `RESULTADOS_PASO` (Favorable / Con observaciones / No favorable). NO se guardan: se DERIVAN en cada lectura de los registros reales (prefiltro, `p.score`, `Entrevista`, `Evaluacion` ligada por `Evaluacion.paso_id` o por tipo, expediente, `TareaOnboarding`). Lo único guardado son las decisiones de RH (`Postulacion.proceso_estado`: omitida/cancelada con quién, motivo y autorización). Cada paso en espera dice EXACTAMENTE qué falta (`espera`: «Falta comprobante de domicilio», «Falta completar: Psicométrica», «Falta el consentimiento médico del candidato», «Falta la revisión de RH») y no frena a los demás.
- Compuerta: avanzar (PATCH de etapa, «Iniciar Onboarding», crear entrevista humana) exige que los OBLIGATORIOS de las etapas que se dejan atrás cumplan su condición (`proceso.faltantes`); si no → 409 con la lista. Las etapas sin pasos obligatorios nunca bloquean. Omitir un obligatorio = justificación (≥10 caracteres) + permiso `Usuario.autoriza_omisiones` (casilla en Configuración → Usuarios; el Administrador siempre) — sin él 403; en el PATCH de etapa es `omitir_obligatorios: true` + `comentario`. Un obligatorio «Completada · No favorable» bloquea igual y NUNCA descarta (RH decide).
- Avance automático: interruptor por etapa (`proceso.etapas[etapa].avance_automatico`, apagado por defecto). Cuando todos los obligatorios de la etapa cumplen su regla, `proceso.avanzar_si_corresponde` mueve a la SIGUIENTE ETAPA CON PASOS (salta las vacías) con la MISMA `candidatos.aplicar_movimiento(automatico=True)`; nunca sale de Contratación (Onboarding solo con «Iniciar Onboarding») ni de Onboarding, nunca reabre ni descarta; un bloqueo (p. ej. sin consentimiento) queda en bitácora `avance_automatico_detenido`. Se dispara tras: prefiltro Zero-Touch (con proceso, el prefiltro «cumple» ya no salta solo a Filtro Red Human ni invita a videollamada si el proceso no tiene Entrevista Red Human), Entrevista Red Human evaluada, resultado de evaluación (RH o liga) y revisión de RH. Siempre vía `avanzar_seguro` (nunca rompe la acción que lo dispara).
- Ejecución conectada: «Iniciar» en el seguimiento abre «Agregar evaluación» precargada (`paso_id`, evaluador = usuario responsable del paso); la entrevista humana genera su guion según `tipo_entrevista` (`TIPOS_ENTREVISTA_HUMANA` → `ia.guion_entrevista_humana`, demo sin clave; `Evaluacion.guion`, visible en la tarjeta y en la liga del evaluador); la Entrevista Red Human usa el enfoque de su paso (`proceso.enfoque_entrevista_agente`, sigue habiendo SOLO 2 enfoques); la médica sigue bloqueando la captura hasta el consentimiento. Plazo vencido (desde `Postulacion.etapa_desde`, que fija un listener de `etapa`, o la última dependencia cumplida) = SOLO alerta.
- UI: ficha → pestaña «Seguimiento» (primera si `tieneProceso`; `components/dashboard/procesos/seguimiento-proceso.tsx`): arriba etapa actual + siguiente acción principal (+ alertas y aviso de versión nueva); abajo los pasos por etapa con Nombre, Responsable, Estado (+ qué falta), Resultado (+ «Revisado por») y Acción; «…» por paso = Omitir / Cancelar (modal con justificación) y Reactivar. La evaluación integral con proceso toma de él las validaciones obligatorias (`evaluacion_integral._validaciones_de_proceso`).
- Tabla `plantillas_proceso` en el paso NO fatal (`TABLAS_MODULOS_RH`, sin FK). Ejemplos listos = los tres escenarios de validación (`proceso.PROCESOS_EJEMPLO`). Regresión: `scripts/verificar_proceso_configurable.py`.

## Canal Telegram (2026-10-06)

- Telegram es SOLO infraestructura de entrega/recepción; no hay lógica de negocio propia (nada de etapas de otros clientes). `services/telegram.py` = cliente HTTP directo a la Bot API (`llamar` NUNCA lanza: `{"ok": False}`), envíos (`enviar_texto`, `enviar_boton`, `enviar_lista`, `enviar_documento`), `descargar_archivo`, normalización de Updates y deep links. Variables SOLO en el `.env`: `TELEGRAM_BOT_TOKEN`, `TELEGRAM_WEBHOOK_SECRET` (opcional; si falta se deriva del token), `TELEGRAM_BOT_USERNAME`. Sin token, todo sale por WhatsApp. Registro: `scripts/configurar_webhook_telegram.py --url https://…/api/webhooks/telegram`.
- Fachada ÚNICA: el negocio sigue llamando `services/whatsapp.py` (`enviar_mensaje`, `enviar_plantilla*`, `enviar_lista_interactiva`, `enviar_con_boton`, `enviar_documento`, `descargar_media`); cada envío pregunta a `services/mensajeria.resolver` y delega en Telegram si toca. Nunca llamar a `services/telegram.py` desde flujos de negocio.
- Canal por Cuenta: `Cuenta.canal_mensajeria` ∈ `CANALES_MENSAJERIA` (whatsapp | telegram | ambos; Configuración → Cuentas → «Canal con candidatos»). Reglas del selector: (1) al responder a un mensaje entrante, a ESA persona se le contesta por el canal por el que escribió (`mensajeria.en_conversacion`); (2) envíos al candidato marcan su Cuenta con `with mensajeria.de_cuenta(p.cuenta_id)` (o se infiere de la persona candidata con ese teléfono); `ambos` = el canal por el que escribió al último; (3) a RH, Cliente y entrevistadores no se les marca Cuenta (`notificaciones` solo la marca si `destinatario_tipo == "candidato"`). Telegram no tiene plantillas ni ventana de 24 h: las plantillas salen como su texto. Alcance de webhooks: `mensajeria.alcance_canal` (WhatsApp no entra a Cuentas «solo Telegram»; Telegram solo a telegram/ambos).
- Webhook `POST /api/webhooks/telegram` (`routers/webhooks_telegram.py`): valida `X-Telegram-Bot-Api-Secret-Token` (403; sin token 503), dedupe PERSISTENTE por `update_id` (`updates_telegram`), 200 inmediato + BackgroundTasks con sesión propia. El Update normalizado (`telegram.parsear_update`: texto, callback_query, contact, photo, document, `/start <payload>`) entra a `webhooks.procesar_entrante` — la MISMA función que usa WhatsApp (menú, aviso de privacidad y consentimiento explícito, prefiltro, documentos en Contratación/Onboarding). `Mensaje.canal` registra «telegram» (`mensajeria.canal_registro`); la lógica sigue usando «whatsapp» como canal de chat.
- Identidad: `chats_telegram` (chat_id ↔ teléfono a 10 dígitos) vía botón nativo «Compartir mi número» (`request_contact`); solo se acepta el contacto PROPIO. Toda la plataforma sigue identificando por teléfono; el chat_id solo vive en esa tabla. Persona nueva = fuente «Telegram», postulación con origen `telegram`.
- Deep links (`/start <payload>`, `[A-Za-z0-9_-]`, ≤64): `vac_<VAC-####>` = elegir esa vacante; `p_<token>` = la postulación (`Postulacion.telegram_token`, 16 hex, se reutiliza; solo sirve desde el chat con el MISMO teléfono de la postulación, si no → rechazo + bitácora `telegram_liga_rechazada`); `p_<token>_<paso>` = ese paso del proceso configurable. Si llega antes del contacto, el payload espera en `ChatTelegram.inicio_pendiente`. Qué responder lo decide el proceso: `services/canal_proceso.py` (`respuesta_paso`, `seguimiento`) traduce el estado DERIVADO del paso a un mensaje con UNA liga existente (formulario, sala de Entrevista Red Human, consentimiento médico, otro sistema/proveedor, expediente) — nunca muestra resultados ni dictámenes al candidato y nunca mueve etapas. Con proceso, la respuesta fija «post-completo» del chat también sale de `canal_proceso.seguimiento`.
- RH: el seguimiento (`GET /procesos/postulaciones/{codigo}`) trae `telegram {disponible, liga, pasos}` si la Cuenta atiende por Telegram → «Copiar liga de Telegram» (cabecera y «…» de cada paso). `/candidatos/postular` regresa `telegram` (deep link) y el portal muestra «Continuar en Telegram»; con «solo Telegram» no se intenta la plantilla de WhatsApp (el bot no puede escribir primero).
- Portal y canal (2026-10-06): «Ver Bolsa de Trabajo» abre `/portal?cuenta=<id de la Cuenta actual>`; `GET /vacantes/publicas` acepta `?cuenta=` o `?cuenta_id=` y regresa la Cuenta + las vacantes de sus Clientes. Detalle público de vacante y `/postular` traen `mensajeria.canales_publicos(v)` (`canalCandidatos`, `telegramBotUsername`, `telegramLiga` = `vac_<VAC-####>`, `whatsappLiga`); «Postulación exitosa» muestra Telegram, WhatsApp o ambos según eso; su botón de Telegram usa SIEMPRE la liga `p_<token>` de la postulación (`telegram` de `/postular`, amarrada al teléfono del formulario), nunca `vac_` (esa es para ligas compartidas/portal). `/start vac_<VAC>` se resuelve en `webhooks_telegram._iniciar_vacante` (selección EXPLÍCITA): vacante no disponible → aviso + menú; postulación activa a esa vacante → se retoma; si no, nace en la Cuenta de la vacante (congela el proceso) y el agente manda el aviso de privacidad. El código NUNCA entra como texto del candidato. Sin Cuentas con Telegram el bot contesta un aviso (nunca silencio).
- Tablas `chats_telegram` y `updates_telegram` en el paso NO fatal (`TABLAS_MODULOS_RH`, sin FK). Regresión: `scripts/verificar_telegram.py` (Bot API simulada, sin red).

## Operación de actividades · trazabilidad por destinatario · flujos de dos fases (2026-10-08, todas las Cuentas)

- «Iniciar» en UN paso (`services/actividades.py`, `POST /procesos/postulaciones/{codigo}/pasos/{paso}/iniciar`): ejecuta lo que trae la ruta (batería, usuario responsable; responsable RH → responsable de la vacante o quien inicia). Solo si falta un dato CRÍTICO regresa `faltan` (`evaluador` para médica, socioeconómica, entrevista humana sin usuario o responsable externo; `correo`/`pruebas` en psicometría) SIN crear nada; si la actividad ya tiene evaluación viva regresa esa (`yaExistia`), nunca duplica. Crea con `crear_evaluacion` / `asignar_psicometria` de siempre.
- Actividad adicional: va en la etapa ACTUAL (o una posterior); nunca en una anterior. Un paso `adhoc` puede ir en cualquier etapa aunque su tipo no la liste.
- Compuerta: revisa TODAS las obligatorias desde `proceso.etapa_base` (se fija al congelar y al «Aplicar versión vigente») hasta la etapa destino (`proceso.desde_compuerta`). Rutas sin `etapa_base` (anteriores) conservan la revisión de la etapa actual. Solo bloquean «Requiere completarse» / «Requiere aprobación» (`condicion` del paso); opcionales y omitidas no.
- «Enviada» YA NO es estado. `EnvioActividad` (`envios_actividad`, paso NO fatal, sin FK) = una fila por canal y por destinatario (`candidato | medico | entrevistador | evaluador | rh | cliente`) con `intento → enviado | fallido`, y `entregado`/`fallido` por acuse de WhatsApp (`whatsapp.acuses_de_entrega` → `envios.actualizar_por_mensaje`, por `mensaje_id`). Una llamada = un `lote`; se muestra el último por destinatario y por motivo. Todo envío nuevo pasa por `services/envios.registrar` (también avisos del motor y la liga de documentos). Evaluaciones previas se leen de sus eventos «envio» (`envios.resumen_legado`); respaldo opcional: `scripts/migrar_envios_actividad.py` (simulación por defecto, `--forzar`, idempotente).
- Estado visible = cuello de botella real (`proceso.ESTADOS_UNIFICADOS`): Sin iniciar · Esperando candidato / referencias / consentimiento · Esperando médico/entrevistador/evaluador (`esperando_evaluador`) · Pendiente de resultado · En curso · Pendiente de revisión · Completada · Aprobada · No aprobada · Omitida · Error. Nadie recibió nada todavía → «Sin enviar»; el último envío a quien debe actuar falló → «Error». En la psicometría simple la clave `enviada` se conserva y se muestra «Esperando candidato».
- Reenvíos granulares (`reenvios` del paso, `POST …/pasos/{paso}/reenviar {a}`): «Reenviar al candidato / al médico / al entrevistador / al evaluador», cada uno con SU liga (consentimiento, referencias, prueba, otro sistema, cita, sala, documentos). Nunca cambian estado ni reinician la actividad.
- UI: UNA acción principal (`siguienteAccion`); cada actividad solo muestra estado + «…» armado por la API (`menu`, nombres estandarizados: la acción propia, Abrir liga, Copiar liga, Reenviar al…, Registrar resultado, Reintentar sincronización, Omitir actividad, Reactivar; sin duplicados y sin la acción que ya es el botón principal).
- Médica ESTRICTA: crearla manda SOLA la solicitud de consentimiento al candidato; el médico no recibe nada hasta que acepte (entonces le sale sola su liga). Si rechaza, la evaluación se CANCELA sola y la actividad queda «No aprobada» (bloquea; RH descarta u omite).
- Referencias en DOS fases (`Evaluacion.referencias/referencias_token/referencias_capturadas_en`): crearla manda al candidato su liga EXCLUSIVA `/referencias/{token}` (1-5 contactos: nombre, empresa y teléfono o correo); al evaluador no le sale nada hasta que capture; al capturar recibe su liga y dictamina CADA contacto (`POST /evaluaciones/publica/{token}/referencias/{rid}` o `POST /evaluaciones/{codigo}/referencias/{rid}`). El resultado general usa el formulario único.
- «Registrar resultado» (`POST …/pasos/{paso}/resultado`, multipart): lo hecho fuera del sistema se guarda en la evaluación de la actividad (o en una nueva `registro_directo` ligada a ella, nunca otra), con dictamen, quién la aplicó (`realizada_por`) y quién capturó (la sesión). La médica sigue exigiendo consentimiento otorgado. Captura manual = prioridad: un resultado tardío del proveedor NO la sobrescribe ni consulta su API (`sev.recuperar_resultado` → evento `resultado_proveedor_posterior`).

Solo `fallida` muestra «Reintentar sincronización» y la reintenta el job `sincronizacion_psicometrias` (30 min; esperas 1/3/12/24 h, máx. 4). Nunca se consulta la API sin falla confirmada (saldo compartido con producción).
- Pruebas sin API (`psicometricas.PRUEBAS_SIN_API`, p. ej. «Persona bajo la lluvia», proyectivas; o IDs fuera del catálogo oficial): el catálogo las guarda como «Carga manual», `_catalogo_integrado` las excluye y asignarlas por API → 400 que pide evaluador o registro manual.
